# Test Case: [TC-012] — Contact form builds a mailto draft with the entered values

**Priority:** P1
**Status:** Inferred from exploration, not yet verified
**Source:** scenario-mapper row S012

## Preconditions
- Anonymous browser session.
- A way to intercept the mailto: handoff (Playwright `page.on('popup')` is the cleanest; on a desktop runner, an OS-level mail client is acceptable but not required).

## Test data
- Contact URL: `https://web.dev.puku.sh/contact`
- Name: `QA Tester`
- Work email: `qa+<unix-timestamp>@example.com` (use a sandbox domain; this form does not send a real request, but a real domain in the body is clearer for debugging)
- Topic: `Billing`
- Product: `Puku CLI` (default)
- Message: `This is a sanity-check message generated by the QA flow runner.`

## Steps

| # | Action | Expected Result |
|---|---|---|
| 1 | Navigate to `https://web.dev.puku.sh/contact` | Page loads; H1 reads "Talk to a person." |
| 2 | Inspect the "Name" textbox (placeholder "Your name") | Visible and empty |
| 3 | Type `QA Tester` into the Name textbox | Textbox value equals `QA Tester` |
| 4 | Inspect the "Work email" textbox (placeholder "you@company.com") | Visible and empty |
| 5 | Type the test work email into the Work email textbox | Textbox value equals the test work email |
| 6 | In the topic group, click the "Billing" button | The "Billing" button gains the pressed/active state; "Support" loses it |
| 7 | Inspect the "Product" combobox | Default selection is "Puku CLI"; this is acceptable — leave it as is |
| 8 | Inspect the "Message" textbox (placeholder "What happened, and what did you expect?") | Visible and empty; character counter reads "0/1000" |
| 9 | Type the test message into the Message textbox | Character counter updates; textbox value equals the test message; counter is ≤ 1000 |
| 10 | Click "Open email draft →" | A new tab/window opens OR a `mailto:` navigation is intercepted. The destination URL starts with `mailto:`. The URL's `to` is `support@puku.sh` (the Billing topic routes to Support, not sales). The `subject` parameter is URL-encoded and contains the topic ("Billing" or similar). The `body` parameter contains the test Name, the test email, the chosen Product, and the test message. |
| 11 | Inspect the network log for a POST to the form endpoint | No POST was sent. The submit button is a mailto: handoff, not a server form submission. |

## Postconditions
- The OS email client may have been launched. If a real client was invoked and a draft was created, close the draft window/tab to avoid clutter.
- No server-side state was created.

## Notes
- This form does NOT POST to a server. Do not assert on a 200 response from a form endpoint; assert on the `mailto:` URL.
- The Topic → recipient mapping is: Support → `support@puku.sh`; Team plan / Billing → likely also `support@puku.sh`; Press → `press@puku.sh` (not present in the test); Other → defaults to support. Verify on a real run; the spec allows either.
- Headless runners should attach a `page.on('popup')` or `page.on('framenavigated')` listener before step 10 to capture the mailto URL.
